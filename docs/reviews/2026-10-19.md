## Suggested change

Two repeats, each written as a proposal Marina can approve or turn down. The
Gemini 429s were the largest group but are not one of them: that was a
one-off billing lapse, now closed, and failover covered it.

1. **Tell the choosing model how many picks to return when the shelf is
   short** (affects `docs/specs/recommendation.md`, prompt `recommend_v6`).
   - *What is wrong.* `recommend_v6` asks for "exactly five books", gives
     the short-list exception ("If the list has fewer than five books,
     recommend all of them") as a later bullet, then closes with "check
     each of your five titles". On a three- or four-book list GPT-5.4 mini
     followed the five.
   - *How the rows show it.* Choosing rows 174, 175, 238, 239: two days,
     four rows, all "expected N, got 5". The same rule also pushes the
     model to fill five slots with weak matches when it should not, as in
     recommendation 294, where three reasons admit the pick is not in the
     reader's genre.
   - *What to change.* A `recommend_v7` that states the number in the
     request, built from the list length: "Recommend exactly N books" with
     N = min(5, list length), and "check each of your N titles". The
     wrong-count check in `recommendation.md` stays as it is. Also add the
     two short-shelf photos (rows 174/175 and 238/239) to the test set with
     labels, so the check covers this case at all.
   - *How we would know it worked.* `research.check` passes against the
     baseline with v7 (no regression on on-list share, overlap, latency,
     cost). The two new short-shelf photos return three and four picks.
     The next reviews show no "expected N, got 5" rows.
   - *Left out on purpose.* Letting the model return fewer than five when
     nothing fits (recommendation 294) changes the product and the save-rate
     denominator. It needs its own decision, not a prompt tweak.

2. **Cap Gemini 3.8 Flash's reasoning in reading** (affects
   `docs/specs/model-router.md`'s config and the `gemini-flash` entry in
   `config/models.toml`).
   - *What is wrong.* Gemini runs at its default thinking level, and on
     dense shelves that thinking uses 4,800 to 6,300 of the 8,192-token
     budget before the JSON is done.
   - *How the rows show it.* Reading rows 763 (app), 1031 and 1847 (test
     set): three truncations in three weeks, each followed by a Sonnet
     failover. This is the pattern the last review closed for Qwen and
     Sonnet, now on the primary. Each one costs the reader a second
     reading call (p50 roughly 8 s on Gemini plus 5 s on Sonnet) and
     Sonnet's price.
   - *What to change.* Set `reasoning_effort` on `gemini-flash`, the
     same key that fixed Qwen in 001. Try `"low"` first; Qwen still
     truncated on low and only stopped at `"none"`, so the check should
     compare both. Raise the budget instead only if less thinking costs
     recall. Add row 763's photo to the test set
     with labels.
   - *How we would know it worked.* `research.check` with Gemini on low
     shows no recall or invented regression and lower p50 latency and
     cost. Gemini `truncated` failovers drop to zero over the next reviews.
