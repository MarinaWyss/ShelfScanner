## Suggested change

Both patterns repeat, and both are the same thing: a stage primary with no key
where the app runs. The previous review said to treat that as a bug if it
outlived the keys arriving, and for the OpenAI key it has.

**What is wrong.** A `config` error is deterministic — the call cannot
succeed until a key changes — but the router retries it on every scan, so each
app scan pays a doomed provider call and then runs the fallback. Nothing
surfaces that: the app silently serves the pair `research.check` does not gate
(Sonnet reading, Haiku choosing) while the dashboard's app latency and cost
describe that pair, not the configured one. The review's own counting hides
the size of it twice over: the legacy error text splits one cause into two
groups, and the window starts on the previous review's last day, so rows 50,
51, 188 and 189 are counted in two consecutive reviews.

**How the rows show it.** All 9 app failovers in this window are `config` — 5
of 5 reading rows, 4 of 4 choosing rows. Four of those nine are new since the
previous review, so the pattern is growing, not closing. The cost is not only
wasted calls: the one app scan that never reached picks (choosing row 50) is
the scan where the doomed primary call handed choosing to a rate-limited
fallback.

**What to change.**

1. In the router, remember a `config` failure: the first one for a model marks
   it unavailable for the rest of the process (or a few minutes), and later
   scans call the fallback directly. The first row still records
   `failover_from` and `failover_error`, so the review sees the cause once
   rather than once per scan.
2. Make the degradation visible without reading rows: check the configured
   primaries' keys at startup and put a line on `/admin` — "reading: primary
   `google/gemini-3.8-flash` unavailable (`GEMINI_API_KEY` not set), running
   on `sonnet`".
3. Fix the review's two counting defects: map a bare `<PROVIDER>_API_KEY is
   not set` head to `config` in `research.review.error_kind` (the router
   already carries the same legacy allowance in `FAILOVER_ERROR_PREFIXES`),
   and start the window the day after the previous review file, not on it.

Not code, and not in scope for that proposal: the reading failovers end when
the Google project has credit, and the choosing ones when the app's checkout
has the OpenAI key. Keys load from `REPO_ROOT/.env`, which is per checkout, so
a worktree or a deployment without that file is the likely reason the eval saw
the key and the app did not. That is worth confirming before anything is
built, because if the app is reading a different `.env` than the eval, only
item 2 above would have caught it.

**How we would know it worked.** `/admin` shows the degraded line while a key
is missing and no line when both are in, with a test for each. Next week's
review shows app failovers at most one per stage per process instead of one
per scan, no app scan lost to a fallback error, and completion no lower. The
config groups collapse to one per model, and no row appears in two consecutive
reviews. `research.check` still passes: the path with keys present is
untouched.

**Specs affected.** `docs/specs/model-router.md` (Failover, Guards) and
`docs/specs/monitoring.md` (the page's error split, and the weekly review's
grouping and window). Change 010's environment-variable list should carry both
provider keys so a deployment cannot repeat this.
