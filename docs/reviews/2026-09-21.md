## Suggested change

Two, the first the one that costs a reader something.

**1. A short shelf should not fail the scan.** *What is wrong:* when the
catalogue check leaves fewer than five titles, GPT-5.4 mini still returns five,
`recommend.py` sets `error = "expected N recommendations, got 5"`, and per
`web.md` the reader gets the "Choosing failed" panel with that string and a "Try
again" — no picks, on a shelf that had three or four good books on it. *How the
rows show it:* four of 34 app scans in this window (rows 174, 175, 238, 239), on
two separate days, four times out of four that the list was short. The test set
shows none of it because `research.matrix llm` passes no verified list, so its
lists are never short — this failure only exists on the path a reader uses.
*What to change:* two small things, either or both. Build the number into the
prompt from the list length ("Recommend exactly three books") instead of the
static "exactly five" plus a trailing conditional the model skips; and, when the
reply is longer than the list allows, keep the on-list picks in rank order, show
them, and record the surplus in the row rather than discarding the answer. The
hard validity check stays as it is, and so does logging the count as a finding —
`model-router.md` is right that a wrong count is a finding about the model and is
not retried; the argument here is only that a finding should not cost the reader
the picks. *How we would know it worked:* no `expected N recommendations, got M`
rows in the next two reviews, `research.check`'s choosing on-list share still
1.00, and app scans complete above 28/34. *Specs affected:*
`docs/specs/recommendation.md` (the wrong-count rule), `docs/specs/web.md` (the
failure panel), prompt `recommend_v6`. Related and worth folding in: the drops
that shorten the list are partly the lookup follow-ups already carried forward
from 007 in `docs/changes/README.md`, and partly the invented titles
`research.check` is currently failing on.

**2. A dead primary should be called once, not 494 times.** *What is wrong:* the
reading primary has now answered no app scan in two consecutive review windows —
last week for want of a key, this week `RESOURCE_EXHAUSTED: prepayment credits
are depleted` — and each time the router called it again on every single call.
*How the rows show it:* 14 app and 480 test-set failovers off one cause across
roughly eight nights, on top of last week's three, and a week of nightly eval
numbers that are Sonnet's recorded under a Gemini failover. *What to change:*
after a few consecutive hard provider failures on a stage, stop calling that
primary for the rest of the run and say so once, instead of paying its latency on
every call; and make the nightly eval say loudly (or refuse) when the stage
primary did not answer, so a week of nights cannot quietly stand in for it. The
billing itself is Marina's to top up, not a code change. *How we would know it
worked:* reading failovers back near zero in the next review, the report's
per-model table showing Gemini rows for the nights in the window, and
`research.check`'s reading row being the primary's own numbers. *Specs affected:*
`docs/specs/model-router.md` (Failover), `docs/specs/monitoring.md` (what the
failover count means).

Watching rather than proposing: the two Gemini truncations at 8,192 tokens (rows
763 and 1031). If a third appears next week, propose setting `reasoning_effort`
for `gemini-flash`, which `config/models.toml` already names as the lever.

Neither of these is approved by being written here; each needs a proposal in
`docs/changes/` and Marina's yes (009 D2).
